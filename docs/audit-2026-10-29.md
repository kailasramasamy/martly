# Robustness Audit — 2026-10-29

Read-only audit of api, admin, mobile, web and shared. 8 auditors, one per risk area. A separate skeptic re-checked every P0/P1 against the code and tried to refute it. All 30 P0/P1 reports survived; they collapse to the 18 root causes below. P2/P3 are single-pass (not adversarially verified).

**Raw counts:** 128 findings (P0 9, P1 21, P2 78, P3 20) → after dedup: **4 P0, 14 P1, ~55 P2, ~20 P3.**

Severity: **P0** money loss / auth bypass / cross-tenant leak · **P1** users will hit it, or exploitable abuse · **P2** edge cases, perf, visible inconsistency · **P3** hardening.

---

## P0 — fix before anything else

| # | Issue | Where | Failure |
|---|---|---|---|
| 1 | **Order payment verify not bound to the order** | `api/src/routes/orders/index.ts:1105` | The signature check is HMAC(`order_id|payment_id`) over the *body's* values. It never compares `body.razorpay_order_id` with `order.razorpayOrderId` or the amount. Pay ₹1 for a wallet recharge, replay that triple against a ₹5,000 order → order marked PAID + CONFIRMED. |
| 2 | **Membership verify not bound to plan/amount** | `api/src/routes/memberships/index.ts:282` | `planId` and `previousMembershipId` come from the query string. The payment is only checked to match its own order id. Any ₹1 payment buys the most expensive plan of any org. |
| 3 | **Cancel / status change has no compare-and-set** | `api/src/services/order-cancel.ts:114`, `routes/orders/index.ts:696-745` | The status is checked on a plain read outside the tx, and the update is `where: {id}`. Double-tap Cancel, customer racing staff, or the expiry job racing a payment → wallet refunded twice, loyalty returned twice, stock released twice. Double DELIVERED → stock deducted twice, loyalty/referral/door-refusal credit paid twice. |
| 4 | **Wallet / loyalty double-spend** | `routes/orders/index.ts:489-595` | `findUnique` balance → unconditional `decrement` under READ COMMITTED. 10 parallel ₹500 orders against a ₹500 wallet → 10 confirmed orders, balance −₹4,500. The same pattern is in admin DEBIT and the subscription scheduler. |

**Fix pattern (all four):** the server binds the payment to the record it settles (stored `razorpayOrderId`, fetched amount = expected amount, plan from the stored Razorpay order notes and not the query). Every money/status mutation uses a conditional update inside the tx (`updateMany where {id, status: {in: [...]}}` → abort if `count === 0`; `walletBalance: {gte: x}` on decrement), plus a DB `CHECK (wallet_balance >= 0)` and `CHECK (loyalty_points >= 0)`. `releaseStock` moves inside the cancel tx.

## P2 — grouped by theme

**Order & checkout correctness**
- Float total vs Decimal wallet balance → wallet-covered order stuck unpaid (`orders/index.ts:455`)
- Delivery fee/serviceability uses client coordinates, not the saved address (`orders/index.ts:333`)
- Empty `items` array accepted (`shared/schemas/index.ts:478`)
- Orders can be placed on a non-ACTIVE store (`orders/index.ts:198`)
- `settleOrderPayment` can resurrect a concurrently cancelled order (`order-payment.ts:51`)
- Unpaid online orders older than 24h never expire (`notify/order-alerts.ts:98`)
- Delivery slot capacity checked before the tx → oversell (`orders/index.ts:434`)
- Stock reserved in cart order → two overlapping carts can deadlock (`orders/index.ts:466`)
- Loyalty redemption can be fractional against an Int column → checkout 500 (`orders/index.ts:522`)
- Return request accepts duplicate `orderItemId` → inflated refund (`return-requests/index.ts:60`)
- Review re-approval awards loyalty every time; `storeId` client-chosen (`reviews/index.ts:306`)
- Refunding an ad order/plan doesn't revoke what it granted (`marketing/billing.ts:190`)
- Admin wallet view shows the customer's cross-org history (`wallet/index.ts:147`)
- Deleting a slot silently turns booked scheduled orders into express (`delivery-slots/index.ts:135`)

**Delivery & schedulers**
- Trip cancel / rider assign / failDelivery are unguarded updates; validation outside the tx → one order on two trips (`delivery-trips/index.ts:247`, `trip-ops.ts:59`)
- All `setInterval` schedulers: no overlap guard, no cross-instance lock; campaign sender can strand SENDING (`delivery-planning-scheduler.ts:56`, `notification-scheduler.ts:25`)

**Security / ops**
- JWT/OTP/signed-link secrets fall back to a hardcoded default; no boot env validation (`app.ts:116`)
- Global error handler leaks raw 5xx/Prisma messages (`app.ts:142`)
- Uploads accept non-images with a client-supplied content type, open to any customer (`uploads/index.ts:32`)
- WebSocket JWT in the query string → in request logs (`websocket.ts:12`)
- Web JSON-LD uses raw `JSON.stringify` → `</script>` injection from catalog data (`web/src/lib/seo.ts:67`)
- No Railway healthcheck; `/health` doesn't touch the DB (`railway.toml:18`)
- No timeouts on outbound HTTP (geocode on checkout path, Places, MSG91, Routes, Anthropic/OpenAI) (`lib/geo.ts:34`)

**Performance (DB)**
- Missing indexes: `order_items(order_id)`, `order_items(product_id)`, `orders(user_id)`, `orders(store_id, created_at)`, slot/date, trip, `razorpay_order_id`; `product_variants(product_id)`, `store_products(product_id)`; the `(store_id, product_id)` unique was dropped (`schema.prisma:468, 957, 1096`)
- Trigram + FTS indexes on `products.search_text` / `search_aliases.alias` dropped in `20260302123022_add_membership_plans` and never recreated
- Search aggregates the store's whole order history per keystroke; suggest runs 8–10 sequential regex scans; zero-result guest searches fan out to 15 queries + an untimed Anthropic call (`search.ts:158, 270`, `search-suggest.ts:152`)
- 31 list routes take an uncapped `pageSize` (incl. public guest routes) (`products/index.ts:239`, `orders/index.ts:72`)
- Legacy `GET /home/:storeId` loads every collection item, uncached, unauthenticated (`home/index.ts:48`)
- Home layout/festival expansion re-run per request; BRAND_CARD joins unindexed order_items (`home/page.ts:116`)
- Offers hub paginates in JS; dashboard loads all period orders into memory; buy-again does in-memory distinct (`store-offers.ts:57`, `dashboard/index.ts:84`, `feed-queries.ts:28`)
- Storefront health computes every store concurrently when snapshots are missing; the 6h timer resets on restart (`storefront/stores.ts:20`)

**Mobile**
- No request timeout anywhere → splash can hang, logout can no-op (`lib/api.ts:57`)
- Forced logout can't unregister the push token → old user's pushes keep arriving (`auth-context.tsx:122`)
- `/auth/me` failure after login → authenticated with `user=null`, staff land on the customer UI (`auth-context.tsx:109`)
- WebSocket created after unmount; reconnects with an expired token (`useOrderWebSocket.ts:37`, `notification-context.tsx:142`)
- Cart only in React state → lost on restart/OS kill (`cart-context.tsx:108`)
- Place-order has no idempotency/re-entrancy guard (`checkout.tsx:377`) — pair with a server idempotency key
- Orders list: no stale-response guard on filter switch (`use-orders-feed.ts:35`)
- Monthly-list debounced edits lost if the screen closes within 600ms (`use-monthly-list.ts:85`)
- Toast/Wishlist context values recreated every render → app-wide re-renders (`toast-context.tsx:105`)
- `referral.tsx` uses non-existent fontSize tokens (10 of the 14 `tsc` errors) (`referral.tsx:289`)

**Admin / web**
- Refresh dedup promise never cleared without a refresh token; order socket reconnects forever with an expired token (`auth-provider.ts:25`, `sharedSocket.ts:24`)
- Delivery board: no stale-response guard (`use-delivery-plan.ts:14`)
- Web root loader failure takes down every page; no error boundary (`web/src/routes/__root.tsx:7`)

**Consistency**
- Variant display rule broken: admin/mobile concatenate `variant.name` + unitValue/unitType or show the raw enum (`admin/src/pages/orders/show.tsx:357` + others)
- Money shown with `toFixed(0)` although orders carry paise → totals visibly don't add up (`mobile/app/checkout.tsx:1227`)

## P3 (hardening)
Failed verify overwrites a PAID order to FAILED · finance can set PAID with no payment record · deleting a used coupon 500s · Places proxy interpolates unvalidated input · `alert_once` never pruned · N+1 in reorder-nudge/wishlist jobs · unauthenticated home events endpoint · public aggregates recomputed per hit (brands, sitemap, tree, facets) · campaign stats N+1 · mobile wishlist/membership/store-resolve/location-picker races · order detail shows "not found" on any error · admin routes not guarded by access control (direct URL) · process hardening (unhandledRejection, SIGTERM) · 32 files over 500 lines incl. giant handlers in orders and subscriptions.

## Fix plan

Each batch: fix → regression test in `apps/api` (`tsx --test`) that reproduces the failure first → local verify → commit. Only 2 tests exist today; these batches add the money-path tests.

| Batch | Scope | Items | Size |
|---|---|---|---|
| **1. Payment binding** | Bind verify to the stored Razorpay order + amount; membership plan from order notes; keep every Razorpay order id per Martly order (new `PaymentAttempt` rows) so the webhook matches any of them; failed verify never downgrades PAID | 1, 2, 5, P3 verify | API + migration |
| **2. Atomic money & status** | CAS status transitions (cancel, PATCH status, settle vs cancel, expiry); conditional wallet/loyalty decrements + CHECK constraints; releaseStock inside the tx; coupon limit check inside the tx + release on cancel; integer loyalty | 3, 4, 7, P2 order items | API + migration |
| **3. Auth hardening** | Token `type` check in `authenticate` + ws; atomic OTP attempts; `@fastify/rate-limit` on auth/OTP/banner events/search + `trustProxy`; phone verified-only + unique; require secrets at boot; WS ownership check; stop leaking 5xx messages | 8–13, P2 security | API + migration; **forces re-login for nobody** (access tokens unchanged) |
| **4. Wallet scope** | Staff DEBIT limited to that org's own credits (or removed); cross-org history hidden | 6, P2 wallet view | API + admin |
| **5. Subscriptions** | Scheduler catches up any `nextDeliveryDate <= tomorrow`, not an exact minute; resume recalculates the date; IST dates; per-(subscription, date) unique key; per-sub wallet re-read inside the tx; share the pricing function with checkout | 14–16 | API + migration |
| **6. DB performance** | Add the missing indexes, recreate trigram/FTS, cap `pageSize` globally, timeouts on outbound HTTP | P2 perf | migration + API |
| **7. Clients** | Mobile auth only clears tokens on a real 401; request timeouts; persist cart; checkout idempotency key; WS token refresh; admin `mode: "off"` + searchable selects; web error boundary + safe JSON-LD; variant/₹ display fixes; mobile `tsc` clean | 17, 18, P2 clients | mobile needs a store build (no OTA) |
| **8. Ops & schedulers** | Advisory-lock wrapper for all schedulers; real `/health` + Railway healthcheck; SIGTERM shutdown; prune `alert_once` | P2/P3 ops | API |

**Suggested order:** 1 → 2 → 3 ship together as one API deploy (they're the exposure). 4, 5 next. 6 is independent and can run in parallel. 7 rides the next mobile build. 8 last.
